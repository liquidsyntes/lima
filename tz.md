# Техническое задание

## Проект
**Название (рабочее):** онлайн-сервис для написания киносценариев в браузере  
**Тип продукта:** web application / SaaS  
**Серверная часть:** Python  
**Клиентская часть:** браузерный интерфейс  
**Назначение:** создание, редактирование, хранение, экспорт и базовая проверка сценариев по профессиональным правилам форматирования.

## 1. Цель проекта
Разработать онлайн-сервис, который работает в браузере и предоставляет пользователю удобный текстовый редактор, специально адаптированный под написание кино- и телесценариев. Сервис должен сочетать современный легкий интерфейс, сценарную логику форматирования, удобную навигацию по структуре сценария и профессиональный экспорт готового текста.[file:16]

Ключевая идея продукта: это не просто «редактор текста», а рабочая среда сценариста, которая помогает писать в корректном индустриальном формате, не заставляя пользователя вручную выставлять отступы, CAPS, выравнивание и типы блоков.[file:16]

## 2. Основание для требований
При разработке необходимо учитывать правила форматирования из предоставленного пользователем PDF-руководства. В частности, система должна поддерживать стандартные элементы сценария: scene heading (slug line), action, character cue, parenthetical, dialogue, transitions, а также учитывать требования к Courier 12 pt, выравниванию, отступам, page-per-minute логике, правилам O.S./V.O., монтажным блокам, флэшбекам, телевизионным актам, титульной странице и экспорту в PDF.[file:16]

## 3. Целевая аудитория
- Сценаристы кино.
- Авторы пилотов и сериалов.
- Редакторы и script doctors.
- Студенты киношкол и курсов сценарного мастерства.
- Независимые авторы, которым нужен браузерный аналог Final Draft / Fade In / WriterDuet с упором на удобство и чистый интерфейс.[file:16]

## 4. Формат конечного решения
Система должна быть реализована как браузерный онлайн-сервис со следующей архитектурной логикой:
- frontend — SPA-интерфейс в браузере;
- backend — приложение на Python;
- хранение данных — база данных + файловое хранилище для экспортов и версий;
- взаимодействие через HTTP API;
- возможность дальнейшего масштабирования до многопользовательского режима и совместной работы.

## 5. Рекомендуемый технологический стек

- **Redis** — опционально для кэша, очередей и временных сессий.

### 5.2 Frontend
В ТЗ не требуется жестко фиксировать frontend-стек, но рекомендуется современный SPA-подход:
- React / Next.js или Vue / Nuxt;
- редактор на базе ProseMirror / TipTap / Lexical / CodeMirror с кастомной сценарной логикой;
- адаптивная верстка, light/dark mode, современная типографика UI.

### 5.3 Экспорт
- Генерация PDF на сервере;
- экспорт в Fountain;
- экспорт в TXT;
- опционально экспорт в FDX-совместимый формат в будущих версиях.[file:16]

## 6. Основные пользовательские сценарии
1. Пользователь регистрируется или входит в систему.
2. Создает новый сценарий, выбирая тип: feature film, TV episode, short film, web series.
3. Пишет текст в специализированном редакторе.
4. Переключает тип текущего блока: slug line, action, character, dialogue, parenthetical, transition, act heading и т. д.
5. Использует клавишу Enter/Tab и горячие клавиши для быстрого перехода между типами блоков.
6. Получает автоматическое форматирование по сценарным правилам.
7. Видит структуру сценария: сцены, акты, флэшбеки, монтажи.
8. Сохраняет черновик автоматически.
9. Просматривает историю версий.
10. Экспортирует сценарий в PDF и другие форматы.[file:16]

## 7. Функциональные требования
### 7.1 Управление пользователями
Система должна поддерживать:
- регистрацию по email и паролю;
- вход/выход;
- восстановление пароля;
- профиль пользователя;
- список проектов пользователя;
- в будущих версиях — совместный доступ по приглашению.

### 7.2 Управление проектами
Для каждого проекта должны быть доступны:
- создание сценария;
- редактирование названия;
- выбор формата проекта: фильм / сериал / короткий метр / веб-сериал;
- выбор языка сценария;
- удаление / архивирование;
- дублирование проекта;
- список последних открытых проектов;
- история версий и дата последнего изменения.

### 7.3 Специализированный сценарный редактор
Редактор должен быть главным экраном системы и поддерживать сценарные сущности как отдельные типы блоков.

Обязательные типы блоков:
- Title Page;
- Scene Heading / Slug Line;
- Action;
- Character Cue;
- Parenthetical;
- Dialogue;
- Transition;
- Shot / Insert / Super — опционально как вспомогательные элементы;
- Montage;
- End Montage;
- Flashback Start / End Flashback;
- Dream Sequence Start / End Dream Sequence;
- Act Heading / End of Act;
- Notes / Comments (служебные, не попадающие в экспорт финального PDF).

### 7.4 Автоформатирование
Система должна автоматически применять форматирование по типу блока:
- slug line — ALL CAPS, flush left, стандартный шаблон `INT./EXT. LOCATION - TIME`;
- action — выравнивание по левому краю, present tense стиль, обычный регистр;
- character cue — центрированное положение и uppercase;
- dialogue — узкий текстовый блок под репликой персонажа;
- parenthetical — отдельный блок меньшей ширины между character cue и dialogue;
- transition — uppercase и выравнивание вправо;
- page numbering — начиная со 2 страницы при экспорте;
- Courier 12 pt в экспортируемом документе.[file:16]

### 7.5 Горячие клавиши и логика Enter/Tab
Редактор должен поддерживать сценарный флоу, чтобы пользователь писал почти не думая о форматировании.

Минимальные правила:
- Enter после Scene Heading -> Action;
- Enter после Action -> Action или Character Cue (по горячей клавише);
- Enter после Character Cue -> Dialogue;
- Enter после Dialogue -> Character Cue или Action в зависимости от контекста;
- Enter после Parenthetical -> Dialogue;
- Tab / Shift+Tab — циклическое переключение типа блока;
- отдельные шорткаты для Scene Heading, Action, Character, Dialogue, Parenthetical, Transition.

### 7.6 Проверка правил форматирования
Редактор должен включать встроенную мягкую валидацию, без излишней агрессии.

Система должна уметь обнаруживать и подсвечивать:
- slug line не в uppercase;
- некорректный формат `INT./EXT. + LOCATION + TIME`;
- слишком длинные action-блоки (например, более 5 строк как рекомендация);
- слишком длинные реплики;
- избыточное использование parenthetical;
- частое использование transitions;
- camera directions в spec-режиме как предупреждение;
- несогласованные имена персонажей;
- путаницу O.S. / V.O.;
- использование нестандартного времени суток, если выбран strict mode.[file:16]

### 7.7 Структурная навигация
Пользователь должен видеть сценарий не только как сплошной текст, но и как структуру.

Необходимы:
- панель сцен;
- список slug lines;
- фильтр по актам;
- отображение количества сцен;
- быстрый переход к сцене;
- индикатор примерного хронометража на основе правила 1 страница = ~1 минута;
- счетчик страниц;
- счетчик слов и символов.[file:16]

### 7.8 Режимы работы
Сервис должен поддерживать минимум 3 режима:
- **Draft mode** — свободное написание, минимум предупреждений;
- **Professional mode** — строгие форматные подсказки;
- **Read mode / Preview** — чистый предпросмотр без UI-шума.

### 7.9 Работа с телевизионным форматом
Для TV-проектов сервис должен поддерживать:
- Teaser;
- Act One, Act Two, ...;
- End of Act;
- Tag;
- опционально multi-camera presets;
- отдельные шаблоны page-range и структуры под half-hour / one-hour.[file:16]

### 7.10 Комментарии и заметки
Необходимо предусмотреть служебные заметки:
- inline notes для автора;
- отдельные заметки к сценам;
- комментарии рецензента / соавтора в будущих версиях;
- возможность исключать заметки из экспорта.

### 7.11 Автосохранение и версии
Система должна:
- автоматически сохранять документ каждые N секунд;
- сохранять revision history;
- позволять откат к предыдущей версии;
- показывать дату и автора изменения;
- поддерживать именованные версии: `v03_submission`, `v04_notes` и т. п.[file:16]

### 7.12 Импорт и экспорт
Обязательный минимум:
- экспорт в PDF;
- экспорт в TXT;
- экспорт в Fountain;
- печатный preview;
- импорт из TXT/Fountain — желательно;
- импорт из DOCX — опционально, с оговоркой о возможной потере форматирования.

К PDF-экспорту предъявляются требования:
- корректный Courier 12 pt;
- page numbers с 2 страницы;
- clean title page;
- аккуратные поля;
- файл без лишних цветных элементов;
- пригодность для отправки как submission PDF.[file:16]

## 8. Нефункциональные требования
### 8.1 UI/UX
Интерфейс должен быть:
- современным;
- легким визуально;
- минималистичным;
- не перегруженным декоративными элементами;
- ориентированным на долгую работу с текстом;
- дружелюбным к большим документам.

Дизайн-принципы:
- светлая и темная темы;
- нейтральная база интерфейса и один акцентный цвет;
- максимум читаемости, минимум визуального шума;
- крупные удобные зоны взаимодействия;
- явный фокус на тексте, а не на панелях;
- плавные, но ненавязчивые анимации;
- адаптация под ноутбук, десктоп и планшет.

Важно: сам UI может использовать современные веб-шрифты, но содержимое экспортируемого сценария должно соответствовать индустриальному стандарту Courier 12 pt.[file:16]

### 8.2 Производительность
- первая загрузка основного интерфейса — максимально быстрая;
- документ на 120+ страниц должен работать без заметных лагов;
- автосохранение не должно мешать набору текста;
- структура документа должна перестраиваться без фризов;
- желательно использовать виртуализацию длинного документа.

### 8.3 Надежность
- защита от потери данных;
- сохранение черновика при обрыве соединения;
- серверная валидация критичных операций;
- резервное копирование данных;
- журналирование ошибок.

### 8.4 Безопасность
- хранение паролей только в захешированном виде;
- JWT / secure session auth;
- HTTPS;
- защита от XSS/CSRF/SQL Injection;
- разграничение доступа к проектам;
- приватность сценарных файлов и экспортов.

## 9. Требования к редакторскому движку
Редактор должен работать не как обычный rich text editor, а как структурированный document editor.

Требования:
- каждый абзац хранится с типом блока;
- логика форматирования зависит от типа блока, а не от ручного стиля;
- запрещено полагаться только на визуальное форматирование через bold/align/margin;
- внутренняя модель документа должна быть пригодна для экспорта, валидации, аналитики и структурной навигации;
- система должна легко поддерживать будущие типы блоков.

Пример модели блока:
- `id`
- `type`
- `text`
- `meta`
- `order`
- `scene_id`
- `revision_id`

## 12. Бизнес-логика форматирования
### 12.1 Slug line
- uppercase;
- формат `INT. / EXT. / INT./EXT.`;
- далее LOCATION;
- затем ` - TIME`;
- допустимые time values: DAY, NIGHT, DAWN, DUSK, LATER, CONTINUOUS, SAME;
- mini-slugs допустимы как отдельный тип/режим блока.[file:16]

### 12.2 Action
- present tense;
- без внутреннего монолога как обязательное правило-подсказка;
- рекомендованная длина 1–5 строк;
- поддержка CAPS для значимых звуковых акцентов.[file:16]

### 12.3 Character cue
- uppercase;
- центрирование;
- поддержка суффиксов `(V.O.)`, `(O.S.)`, `(CONT'D)`.[file:16]

### 12.4 Dialogue
- отдельная ширина блока;
- переносы строк без разрушения структуры;
- предупреждение при слишком длинной реплике;
- поддержка dual dialogue как расширение.[file:16]

### 12.5 Parenthetical
- краткая ремарка;
- только между cue и dialogue;
- предупреждение при чрезмерной длине или слишком частом использовании.[file:16]

### 12.6 Transition
- uppercase;
- выравнивание вправо;
- использовать ограниченно; редактор может показывать warning при злоупотреблении.[file:16]

### 12.7 Title page
- отдельная сущность;
- title, author, contact;
- без номера страницы;
- отдельный шаблон печати и экспорта.[file:16]

## 14. Требования к дизайну
Визуальный стиль должен быть современным и легким, без ощущения «тяжелой офисной программы».

Рекомендации:
- светлый фон с мягкими нейтральными поверхностями;
- чистая типографика интерфейса;
- аккуратные панели и карточки;
- минимальные тени;
- хорошие отступы;
- понятная иерархия состояний;
- отсутствие кричащих градиентов и лишнего декора;
- фокус на спокойной длительной работе автора.

Редактор должен создавать ощущение «тихой профессиональной студии»: текст — главный герой, интерфейс — вежливый ассистент.

## 15. Требования к комментариям в коде
Это обязательное требование проекта.

### 15.1 Общие правила
- Код должен содержать **подробные комментарии**.
- Все комментарии в коде должны быть **только на русском языке**.
- Комментарии должны объяснять:
  - назначение модуля;
  - назначение класса/функции;
  - входные и выходные параметры;
  - сложную бизнес-логику;
  - причины нестандартных решений;
  - сценарную логику форматирования.

### 15.2 Что недопустимо
- комментарии на английском языке;
- формальные бессмысленные комментарии вроде `# функция`;
- отсутствие комментариев в ключевых частях редактора, экспорта и валидации.

### 15.3 Стандарт комментирования
Рекомендуется:
- docstring на русском языке для модулей, классов и функций;
- поясняющие inline-комментарии рядом со сложной логикой;
- единый стиль оформления комментариев по всему проекту.

Пример требования:
> Любая функция, реализующая правила сценарного форматирования, должна сопровождаться понятным русскоязычным описанием: что она проверяет, почему это правило важно и как влияет на итоговый экспорт.

## 16. Ограничения и допущения
- Сервис должен работать в актуальных версиях Chrome, Edge, Firefox, Safari.
- Базовый приоритет — desktop/laptop, но интерфейс должен быть адаптивным.
- На первом этапе не обязательна полноценная совместная работа в реальном времени.
- На первом этапе можно не реализовывать полноценимпорт FDX, если это сильно усложняет MVP.
- Приоритет MVP: сценарный редактор, автоформатирование, навигация по сценам, автосохранение, экспорт PDF.

## 17. MVP-объем
В первую версию обязательно включить:
- аутентификацию;
- создание и хранение проектов;

## 19. Критерии приемки
Проект считается соответствующим ТЗ, если:
- сервис работает в браузере без установки desktop-клиента;
- backend реализован на Python;
- пользователь может создать сценарий и писать его в специализированном редакторе;
- редактор корректно различает типы сценарных блоков;
- основные правила форматирования из приложенного руководства учтены;
- PDF-экспорт выглядит как профессионально отформатированный сценарий;
- UI современный, легкий и удобный для длительной работы;
- проектный код снабжен подробными комментариями на русском языке;
- структура проекта подготовлена к масштабированию.[file:16]

## 20. Формулировка задачи для разработки
Необходимо разработать онлайн-сервис на Python, работающий в браузере, который представляет собой профессиональный редактор киносценариев с автоматическим соблюдением правил форматирования, удобной структурной навигацией, современным минималистичным интерфейсом и возможностью экспорта сценария в индустриально приемлемый PDF-формат. Все ключевые части кода должны быть подробно прокомментированы на русском языке.

## 21. Краткий вывод для команды
Если совсем по-человечески: нужно сделать «спокойный, красивый, профессиональный сценарный редактор», где автор думает о сцене и диалоге, а не о том, сколько дюймов у отступа слева. Но под капотом сервис обязан строго уважать индустриальные правила сценарной верстки и быть технически аккуратным продуктом, а не просто красивой веб-страничкой.[file:16]
